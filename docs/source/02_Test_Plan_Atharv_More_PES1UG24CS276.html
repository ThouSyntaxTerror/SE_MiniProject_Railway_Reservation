1. Introduction

1.1 Purpose

This plan defines the scope, strategy, resources, environment, entry/exit criteria, security validation and traceability for system testing of RRS. The SRS v1.1 is the requirements baseline.

1.2 Objectives

  • Verify all functional, non-functional and security requirements.
  • Verify booking/cancellation invariants under normal, failure and concurrent conditions.
  • Produce repeatable evidence and a requirement-level completion review.

1.3 References

Team E15 RRS SRS v1.1; Team E15 Architecture and Design Specification v1.1; ISO/IEC/IEEE 29119-3:2021 test documentation guidance.

2. Test Items and Scope

In scopeRegistration; authentication; search; availability; booking; history; cancellation; administration; audit; performance; concurrency; restart recovery; accessibility; compatibility; transport, session, credential and authorization security.
Test itemsBrowser UI, REST API, domain services, relational database behavior and payment-simulator integration.
Out of scopeReal card payments, live railway feeds, production disaster recovery, dynamic pricing and wait-list allocation.
AssumptionsSeeded synthetic data, test-only database inspection, configurable payment outcomes and current supported browsers are available.

3. Test Strategy and Approach

3.1 Test Levels

  • Unit: validation, password policy, state transitions and availability calculations.
  • API integration: authorization, database constraints, persistence, idempotency and simulator outcomes.
  • System: passenger/administrator browser workflows, accessibility and compatibility.
  • Non-functional: load, concurrency and restart recovery.

3.2 Techniques

Positive/negative scenarios, equivalence partitions, boundary values, role/ownership checks, duplicate submission, state-transition testing and concurrent final-seat requests are used. Automated checks are preferred for API, load and security work; keyboard and visual compatibility checks may be manual with recorded evidence.

3.3 Test Data

Use synthetic passenger accounts P1 and P2, administrator A1, trips with zero/one/multiple seats, a departed trip, success/failure simulator modes and a 10,000-trip performance seed. Reset independent cases to a known database snapshot.

3.4 Defect Handling

Record case ID, build, environment, reproducible steps, expected/actual results, severity and evidence. Retest a fix and execute affected regression cases. Critical or high defects block exit unless a documented academic-review decision states otherwise.

4. Environment, Responsibilities and Schedule

4.1 Environment

  • HTTPS test deployment and isolated relational test database.
  • Current stable Chrome, Edge and Firefox; 375-pixel and 1280-pixel viewports.
  • Load/concurrency tool supporting at least 50 virtual users and synchronized requests.
  • Authorized, read-only database/log inspection for credential and audit validation.

4.3 Sequence

Baseline documents → deploy/seed → smoke test → functional/security cases → performance/concurrency → accessibility/compatibility → defect retest/regression → traceability and exit review.

4.4 Entry and Exit Criteria

EntrySRS and design baselined; test build deployed; simulator and seed data available; test accounts and evidence repository prepared.
ExitAll ten cases have recorded outcomes; no open critical/high defects; every FR/NFR/SEC statement is demonstrably covered or has a documented follow-up test; evidence is reviewed.

4.5 Risks and Mitigations

RiskMitigation
Environment timing distorts performanceRecord hardware/build/tool versions; warm up; repeat runs using the same seed.
30-minute session test is slowRun the real-duration acceptance check; use configurable time only for earlier regression.
Concurrent requests are not synchronizedUse a barrier so all 20 final-seat requests start together.
Sensitive test data leaksUse synthetic identities and redact tokens/passwords from evidence.

5. Test Design and Validation

A case passes only when every expected result is observed and retained evidence supports the result. Failure of one assertion fails the case until corrected and rerun.

5.2 Test Cases

TC-01 — Registration, Password Boundary and Credential Storage

PreconditionsNo P1 account; authorized test-only read access to user storage and logs.
ProcedureSubmit an 11-character password; submit a valid 12-character password and unique email; repeat the same email; inspect stored credential, response and logs.
Expected11-character input is rejected; valid input creates one account; duplicate is rejected; stored value is a salted adaptive hash and does not equal the password; plaintext appears in neither responses nor logs.
TraceabilityFR-01; SEC-02
EvidenceAPI/UI responses, redacted storage inspection and log search.

TC-02 — Sign-In, Lockout and Authentication Audit

PreconditionsP1 exists and is unlocked.
ProcedureSign in correctly and sign out; submit five incorrect passwords within 15 minutes; attempt a sixth; inspect audit; retry after the 15-minute rejection period.
ExpectedValid login works; invalid responses are generic; sixth attempt is rejected for 15 minutes; success, failures and rejection are audited without submitted passwords; access resumes after the period with valid credentials.
TraceabilityFR-02, FR-09; SEC-02, SEC-04
EvidenceTimestamped responses and redacted audit records.

TC-03 — Search and Availability

PreconditionsMatching, nonmatching, sold-out and multiple-departure trips are seeded.
ProcedureSearch by origin, destination and date; inspect filtering, ordering and every availability value.
ExpectedOnly exact route/date matches appear in departure order; every count is between zero and capacity.
TraceabilityFR-03, FR-04
EvidenceSeed extract and ordered API/UI result.

TC-04 — Successful Booking, History and Audit

PreconditionsP1 signed in; selected trip has one free seat; simulator succeeds.
ProcedureSubmit one booking; query P1 history and audit records.
ExpectedExactly one confirmed booking with unique PNR and one allocated seat; P1 history shows PNR/trip/seat/fare/status; confirmation audit contains actor, action, time and outcome.
TraceabilityFR-05, FR-06, FR-09
EvidenceBooking response, database state, history and audit event.

TC-05 — Payment Failure and Idempotent Retry

PreconditionsP1 signed in; one free seat; known idempotency key.
ProcedureRun with simulator failure; verify state. Then configure success and send the same logical request twice with one new idempotency key.
ExpectedFailure confirms nothing and releases the hold; duplicate success calls return one booking/PNR and allocate one seat.
TraceabilityFR-05; NFR-03
EvidenceResponses, booking count and inventory before/after.

TC-06 — Ownership, Eligible/Late Cancellation and Audit

PreconditionsP1 owns one future confirmed booking and one departed confirmed booking; P2 signed in separately.
ProcedureP2 reads/cancels P1 future booking; P1 cancels it twice; P1 attempts to cancel the departed booking; inspect inventory/refund/audit.
ExpectedP2 gets 403/404 without details; P1’s first eligible cancellation succeeds with one seat release/refund reference/audit event; repeat and late attempts are rejected without further inventory change.
TraceabilityFR-06, FR-07, FR-09; SEC-01
EvidenceResponses, inventory deltas, payment event and audit events.

TC-07 — Administrator Inventory, Authorization and Audit

PreconditionsA1 administrator and P1 passenger exist.
ProcedureP1 attempts administrator create; A1 creates, edits and disables a trip; inspect state and audit.
ExpectedP1 receives 403; A1 changes persist; each change has actor, timestamp, action and outcome.
TraceabilityFR-08, FR-09; SEC-01
EvidenceResponses, final trip state and audit events.

TC-08 — Concurrent Final Seat

PreconditionsExactly one seat; 20 distinct authenticated passengers; simulator succeeds.
ProcedureRelease 20 booking requests simultaneously from a synchronization barrier; inspect bookings and availability.
ExpectedAt most one confirmation; others report unavailable; final count is zero and is never negative.
TraceabilityFR-04, FR-05; NFR-03
EvidenceTool timestamps, responses, booking count and availability history.

TC-09 — Transport, Session and Restart Recovery

PreconditionsHTTPS deployment; P1 session; committed booking exists.
ProcedureInspect transport; sign out and replay token; create a session, wait 30 minutes idle and reuse it; restart application; query health and booking.
ExpectedAuthenticated traffic uses HTTPS; signed-out/expired tokens fail; booking persists; health responds within 60 seconds; logs omit tokens/passwords.
TraceabilityNFR-04; SEC-02, SEC-03
EvidenceTransport capture, timestamped responses, restart log and persisted record.

TC-10 — Performance, Accessibility and Compatibility

Preconditions10,000 trips; 50 virtual users; Chrome/Edge/Firefox; 375px and 1280px viewports.
ProcedureRun 200 searches and 100 bookings at 50 users; complete required workflows by keyboard at both widths in each browser; inspect accessible names.
Expected≥95% searches ≤2s; ≥95% bookings ≤3s under the simulator condition; keyboard completion succeeds; every required control has an accessible name; no primary-form horizontal scrolling.
TraceabilityNFR-01, NFR-02, NFR-05, NFR-06
EvidenceLoad summary, browser/version matrix, screenshots and accessibility report.

6. Test Completion and Deliverables

Evidence includes completed case records, API responses/screenshots, performance summaries, accessibility notes, audit/storage inspection, defect log and final traceability review. A failed case is not waived without a recorded decision and reason.

Execution metadata required per caseBuild, environment, tester, date/time, actual result, evidence link, pass/fail/block status and defect ID where applicable.
Completion reviewTest owner and requirement reviewer confirm evidence and unresolved risks against exit criteria.
